Git en escenarios reales

La hoja de referencia te dice qué hace cada comando. Esta guía te dice cuándo usarlo: busca la situación en la que estás, mira el dibujo de lo que pasa con tus commits y copia los comandos.

Leyenda de los dibujos de commits:

Empiezo un proyecto

Lo que haces una sola vez por computador o por proyecto.

SituaciónEs mi primera vez usando Git en este computador

Seguro
Tu nombre aparece en cada commit que hagas.
Usa el mismo correo de tu cuenta de GitHub, así tus commits quedan ligados a tu perfil.
Los repos nuevos arrancan con la rama main.

Por qué: si no lo configuras, tus commits salen con un autor raro o Git te bloquea el primer commit.

SituaciónTengo una carpeta con código y quiero subirla a GitHub

Seguro
Convierte la carpeta en repositorio (crea la carpeta oculta .git).
Prepara todos los archivos. Antes crea tu .gitignore.
Guarda la primera foto del proyecto.
Conecta tu repo local con el repo vacío que creaste en GitHub.
Sube main y la deja enlazada. Los siguientes push son solo git push.

SituaciónMe unieron a un proyecto que ya existe en GitHub

Seguro
Descarga el código y toda su historia.
Entra a la carpeta; Git ya quedó conectado con origin.

Cuándo NO usar init: si el repo ya existe en GitHub, nunca hagas git init y copies archivos a mano. Clona.

SituaciónNo quiero subir .env, node_modules ni archivos del sistema

Cuidado
Agrega la regla al .gitignore (también node_modules/, .venv/, .DS_Store).
Si ya lo habías subido: lo saca del repo pero lo deja en tu disco.
Registra el cambio.

Ojo: .gitignore solo ignora archivos que Git aún no sigue. Si una contraseña ya llegó a GitHub, mira el escenario de credenciales en Deshacer.

Trabajo del día a día

El ciclo que repites decenas de veces: revisar, preparar, guardar, subir.

SituaciónTerminé un pedacito que funciona y quiero guardarlo

Seguro
¿Qué cambié? Úsalo antes de cada add y cada commit.
Revisa línea por línea lo que vas a guardar.
Prepara solo los archivos de este cambio.
Mensaje en presente que diga qué hace el cambio.
Súbelo cuando quieras respaldo o que otros lo vean.

Regla práctica: un commit = una idea. "Arreglos varios" no le sirve a nadie dentro de tres meses.

SituaciónCambié muchas cosas pero quiero commits separados

Seguro
Git te muestra cada bloque de cambios y respondes y (sí) o n (no).
Revisa lo que ya quedó preparado antes del commit.
Primer commit. Repite add -p para el siguiente.

Cuándo: arreglaste un bug y de paso cambiaste estilos. Son dos commits: si el estilo hay que revertirlo, el bug sigue arreglado.

Trabajo con ramas

Una rama es una línea de trabajo aislada. main debe estar siempre funcionando.

SituaciónVoy a empezar una funcionalidad nueva

Seguro
Parte siempre de main...
...actualizado.
Crea la rama y se pasa a ella (antes: git checkout -b).

Nombres útiles: feature/..., fix/..., docs/... Así el equipo sabe qué es cada rama sin abrirla.

SituaciónMi rama quedó atrasada: main avanzó mientras yo trabajaba

Cuidado

Opción A: merge

Opción B: rebase

Trae lo nuevo de GitHub sin tocar tu código.
A: une main en tu rama con un commit de merge. Seguro siempre.
B: reescribe tus commits encima de main. Historia limpia.

Cuál elegir: rebase solo en ramas tuyas que nadie más usa. Si la rama es compartida, usa merge.

SituaciónTerminé la funcionalidad y quiero que entre a main

Seguro
Sube tu rama a GitHub.
Abre el Pull Request (o hazlo desde la web de GitHub).
Después de que aprueben y unan el PR.
Borra la rama local; ya está dentro de main.

Por qué PR y no merge directo: otra persona revisa el código y el CI corre las pruebas antes de tocar main.

SituaciónHice merge y Git dice CONFLICT

Cuidado
<<<<<<< HEAD
const limite = 10;            // lo que hay en tu rama
=======
const limite = 25;            // lo que viene de la otra rama
>>>>>>> main
Lista los archivos en conflicto ("both modified").
Edita: deja la versión correcta y borra las marcas <<< === >>>.
Marca el conflicto como resuelto.
Cierra el merge.
Salida de emergencia: vuelve a como estabas antes del merge.

No es un error: Git solo te pide que decidas porque dos personas cambiaron la misma línea. Si no sabes cuál va, pregunta a quien hizo el otro cambio.

Trabajo en equipo con GitHub

Tu repo local y el de GitHub no se sincronizan solos.

SituaciónLlego a trabajar en la mañana

Seguro
Ve a main.
Trae y une lo que el equipo subió ayer (pull = fetch + merge).
Vuelve a tu rama y, si hace falta, actualízala con main.

Por qué: entre más tiempo pases sin actualizar, más grandes serán los conflictos.

SituaciónHice push y salió "rejected (non-fast-forward)"

Cuidado

Antes: las historias se separaron

Después de pull --rebase

Trae lo de tu compañero y pone tu commit encima.
Ahora sí entra.

Nunca: git push --force en main o en ramas compartidas para "quitar el error". Borras el trabajo de tu compañero en GitHub.

SituaciónQuiero probar la rama de un compañero

Seguro
Descarga las ramas nuevas de GitHub.
Lista las ramas remotas para ver el nombre exacto.
Git crea tu copia local enlazada a origin/fix/pagos.

Cuándo: para revisar un PR corriendo el código en tu máquina, no solo leyéndolo.

Me equivoqué: cómo deshacer

La pregunta clave siempre es la misma: ¿ya lo subiste con push?

¿Qué quieres deshacer?

Sigue la fila de tu caso. Lo que ya está en GitHub se corrige con un commit nuevo, no reescribiendo la historia.

SituaciónQuiero botar los cambios de un archivo y volver a la última versión

Destructivo
Descarta lo que no has preparado con add.
Si ya hiciste add: lo saca de staging, tu edición se conserva.

Sin vuelta atrás: lo que nunca estuvo en un commit no se puede recuperar. Revisa con git diff antes.

SituaciónEl último commit tiene un error en el mensaje o le faltó un archivo

Cuidado
Reemplaza el último commit con uno nuevo.
Mete el archivo que faltaba sin cambiar el mensaje.

Solo si no hiciste push. amend crea un commit distinto; si ya estaba en GitHub, haz un commit nuevo.

SituaciónHice commits en main cuando debían ir en una rama

Cuidado

Antes

Después

Crea la rama apuntando a tus commits (no se pierden).
Devuelve main a como está en GitHub.
Sigue trabajando donde debía ser.

Requisito: no haber hecho push de main y no tener cambios sin commit (reset --hard los borra).

SituaciónYa hice push de un commit que rompió la app

Seguro
Copia el hash del commit malo (ej. a1b2c3d).
Crea un commit nuevo que hace lo contrario.
Sube la corrección sin reescribir la historia.

Por qué revert y no reset: tus compañeros ya tienen ese commit. revert agrega, no borra, así nadie queda con una historia distinta.

SituaciónHice reset y perdí commits que sí necesitaba

Seguro
Historial de todo lo que hizo HEAD, incluso lo "borrado".
Crea una rama en el punto que quieres recuperar.

Salvavidas: un commit casi nunca se pierde de verdad. reflog los guarda unos 90 días en tu máquina.

SituaciónSubí una contraseña, token o API key a GitHub

Urgente
  1. Revoca la clave en el servicio (AWS, Azure, OpenAI...). Hoy, no mañana.
  2. Genera una nueva y guárdala en .env o un gestor de secretos.
  3. Agrega el archivo a .gitignore y haz git rm --cached.
  4. Si el repo es público o la política lo exige, limpia la historia.
Borra el archivo de toda la historia (herramienta git-filter-repo). Coordina con el equipo: todos deben volver a clonar.

Lo importante: borrar el commit NO basta. Bots escanean GitHub en minutos; asume que la clave ya fue copiada y rótala.

Interrupciones y cambios a medias

Cuando tienes que dejar todo a la mitad.

SituaciónMe piden arreglar un bug urgente y tengo cambios sin terminar

Seguro
  1. Guarda lo que llevas en el cajón: stash
  2. Ve a main y crea fix/...
  3. Arregla, commit, push, PR
  4. Vuelve a tu rama
  5. Saca lo del cajón: stash pop
Guarda los cambios sin commit y deja la carpeta limpia.
Rama del arreglo urgente.
Al terminar el arreglo, regresa.
Recupera tus cambios. git stash list muestra lo guardado.

Alternativa: si el trabajo a medias es grande, haz un commit "WIP" en tu rama y luego lo corriges con amend.

SituaciónNecesito solo UN commit de otra rama

Cuidado
Busca el hash del commit que necesitas.
Copia ese commit a tu rama actual.

Cuándo: un fix urgente quedó en una rama que todavía no está lista para main.

Investigar el historial

Git es también una máquina del tiempo para depurar.

Situación¿Quién cambió esta línea y por qué?

Seguro
Autor, fecha y commit de cada línea entre la 40 y la 60.
Abre ese commit completo: mensaje y cambios.
Toda la historia de un archivo con sus diferencias.

Para qué: entender la intención antes de "arreglar" algo que alguien hizo a propósito. No es para culpar a nadie.

SituaciónAntes funcionaba y ahora no. ¿Qué commit lo dañó?

Seguro
Empieza la búsqueda.
El commit actual falla.
Esta versión funcionaba.
Git te mueve a la mitad, pruebas, dices good o bad, y repite hasta hallar el culpable. Luego reset.

Por qué: en 1.000 commits encuentra el culpable en unos 10 pasos (búsqueda binaria).

Situación¿Qué tiene mi rama que no tenga main?

Seguro
Dibuja todas las ramas en la terminal.
Commits que están en tu rama y no en main.
Cambios que traería tu PR.

SituaciónVamos a publicar una versión

Seguro
Marca el commit actual con un nombre de versión.
Los tags no se suben con push normal.

Para qué: volver exactamente a lo que está en producción con git switch --detach v1.3.0.

Flujo diario y reglas de oro

Si recuerdas solo esto, ya trabajas como en un equipo real.

Un día normal

  1. git switch main
    git pull
  2. git switch -c feature/x
  3. Programa y haz status, add, commit seguido
  4. git push -u origin feature/x
  5. Pull Request, revisión y merge en GitHub
git status es gratis

Úsalo antes y después de cada comando. Te dice dónde estás y qué sigue.

main siempre funciona

Nunca trabajes directo en main. Todo entra por rama y PR.

Commits pequeños

Un cambio, un commit, un mensaje que explique el qué y el porqué.

Pull antes de empezar

Actualizar seguido mantiene los conflictos pequeños.

Lo subido no se reescribe

Si ya hiciste push: revert, no reset. Nada de --force en ramas compartidas.

Secretos fuera del repo

.env en .gitignore desde el primer commit. Si se filtra, rota la clave.

No hay escenarios que coincidan con la búsqueda.

Comandos con la sintaxis actual de Git (switch y restore, desde Git 2.23). En versiones viejas: git checkout -b rama equivale a git switch -c rama y git checkout -- archivo a git restore archivo.
